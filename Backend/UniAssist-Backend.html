1. Overview

The UniAssist backend is powered entirely by Supabase, which provides:

  • PostgreSQL — the primary relational database
  • Supabase Auth — authentication and session management
  • Supabase Storage — file uploads (request attachments, deliverables, resources)
  • Supabase Realtime — live messaging and notification delivery
  • Supabase Edge Functions — server-side logic (payment webhooks, email triggers, quote creation, business rules)

There is no separate Node.js/Express server. All backend logic runs either directly through Supabase's client library (with RLS enforcing security) or through Edge Functions for operations that require elevated privileges or third-party service calls.

Why Supabase

  • Removes the need to build and maintain a separate API server during the early product stage
  • PostgreSQL gives full relational power with foreign keys, constraints, and triggers
  • RLS makes it safe to call the database directly from the frontend without exposing data across users
  • Realtime works out of the box with the existing database — no additional infrastructure
  • Edge Functions allow custom server logic without managing servers

3. Supabase Project Setup

Step 1 — Create Project

  1. Go to supabase.com
  2. Create a new organization: Balerioncodes
  3. Create a new project: uniassist-production
  4. Choose a strong database password — store it securely
  5. Select the closest region to your target users

Step 2 — Install Supabase CLI

npm install -g supabase
supabase login
supabase init          # run inside your project repo
supabase link --project-ref <your-project-ref>

Step 3 — Local Development

supabase start         # starts local Supabase stack (Docker required)
supabase db reset      # applies all migrations from scratch
supabase db diff       # shows pending schema changes
supabase migration new <name>   # creates a new migration file
supabase db push       # pushes migrations to linked remote project

Step 4 — Frontend Client Setup

// src/lib/supabase.ts
import { createClient } from '@supabase/supabase-js'
import { Database } from '@/types/supabase'  // generated types

export const supabase = createClient<Database>(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY
)

Generate TypeScript types from your schema:

supabase gen types typescript --project-id <ref> > src/types/supabase.ts

Regenerate this file every time the schema changes.

4. Environment Variables

Frontend (Vite) — .env

VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-anon-key
VITE_PAYSTACK_PUBLIC_KEY=pk_live_xxxxxxxxxxxx
The anon key is safe to expose in the frontend. It is not a secret. Security is enforced by RLS policies, not by hiding this key.

Edge Functions — Supabase Secrets

Set these via the Supabase dashboard or CLI. Never put these in frontend .env.

supabase secrets set PAYSTACK_SECRET_KEY=sk_live_xxxxxxxxxxxx
supabase secrets set RESEND_API_KEY=re_xxxxxxxxxxxx
supabase secrets set SUPABASE_SERVICE_ROLE_KEY=your-service-role-key
The service role key bypasses RLS. It must only ever be used inside Edge Functions, never in the frontend.

5. Database Schema

All tables use UUIDs as primary keys. All tables include created_at and updated_at timestamps. updated_at is automatically maintained by a trigger.

5.1 profiles table

Extends the Supabase auth.users table. Created automatically on user registration via a trigger.

CREATE TABLE profiles (
  id              UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  full_name       TEXT NOT NULL,
  email           TEXT NOT NULL,
  phone           TEXT,
  university      TEXT,
  department      TEXT,
  level           TEXT,
  student_id      TEXT,
  avatar_url      TEXT,
  role            TEXT NOT NULL DEFAULT 'student'
                  CHECK (role IN ('student', 'admin', 'staff')),
  is_active       BOOLEAN NOT NULL DEFAULT TRUE,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

Trigger — auto-create profile on signup:

CREATE OR REPLACE FUNCTION handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO profiles (id, full_name, email)
  VALUES (
    NEW.id,
    NEW.raw_user_meta_data->>'full_name',
    NEW.email
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION handle_new_user();

5.3 requests table

The central table of the entire application.

CREATE TYPE request_status AS ENUM (
  'DRAFT',
  'SUBMITTED',
  'UNDER_REVIEW',
  'QUOTED',
  'AWAITING_PAYMENT',
  'PAID',
  'ASSIGNED',
  'IN_PROGRESS',
  'REVIEW',
  'COMPLETED',
  'CLOSED',
  'CANCELLED',
  'REJECTED',
  'DISPUTED'
);

CREATE TYPE request_urgency AS ENUM (
  'LOW',
  'NORMAL',
  'HIGH',
  'URGENT'
);

CREATE TABLE requests (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  reference       TEXT NOT NULL UNIQUE,     -- e.g. REQ-10482
  student_id      UUID NOT NULL REFERENCES profiles(id) ON DELETE RESTRICT,
  category_id     UUID NOT NULL REFERENCES service_categories(id),
  title           TEXT NOT NULL,
  description     TEXT NOT NULL,
  subject         TEXT,
  department      TEXT,
  technology      TEXT,
  deadline        DATE NOT NULL,
  urgency         request_urgency NOT NULL DEFAULT 'NORMAL',
  status          request_status NOT NULL DEFAULT 'DRAFT',
  assigned_to     UUID REFERENCES profiles(id),
  progress        SMALLINT DEFAULT 0 CHECK (progress >= 0 AND progress <= 100),
  internal_notes  TEXT,                     -- admin-only notes, never shown to student
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

Reference number generator:

CREATE SEQUENCE request_ref_seq START 10000;

CREATE OR REPLACE FUNCTION generate_request_reference()
RETURNS TRIGGER AS $$
BEGIN
  NEW.reference := 'REQ-' || nextval('request_ref_seq')::TEXT;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER set_request_reference
  BEFORE INSERT ON requests
  FOR EACH ROW EXECUTE FUNCTION generate_request_reference();

5.4 request_status_history table

Records every status change for the timeline view.

CREATE TABLE request_status_history (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  request_id  UUID NOT NULL REFERENCES requests(id) ON DELETE CASCADE,
  old_status  request_status,
  new_status  request_status NOT NULL,
  changed_by  UUID REFERENCES profiles(id),
  note        TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

Trigger — auto-log status changes:

CREATE OR REPLACE FUNCTION log_request_status_change()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.status IS DISTINCT FROM NEW.status THEN
    INSERT INTO request_status_history (request_id, old_status, new_status)
    VALUES (NEW.id, OLD.status, NEW.status);
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER on_request_status_change
  AFTER UPDATE ON requests
  FOR EACH ROW EXECUTE FUNCTION log_request_status_change();

5.6 payments table

CREATE TYPE payment_status AS ENUM (
  'PENDING',
  'PROCESSING',
  'SUCCESSFUL',
  'FAILED',
  'REFUNDED',
  'DISPUTED'
);

CREATE TABLE payments (
  id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  request_id            UUID NOT NULL REFERENCES requests(id) ON DELETE RESTRICT,
  student_id            UUID NOT NULL REFERENCES profiles(id),
  quote_id              UUID NOT NULL REFERENCES quotes(id),
  amount                NUMERIC(10, 2) NOT NULL,
  currency              TEXT NOT NULL DEFAULT 'NGN',
  status                payment_status NOT NULL DEFAULT 'PENDING',
  paystack_reference    TEXT UNIQUE,       -- Paystack transaction reference
  paystack_access_code  TEXT,             -- used to open Paystack popup
  verified_at           TIMESTAMPTZ,      -- set when webhook confirms success
  failure_reason        TEXT,
  metadata              JSONB,            -- raw Paystack response (for auditing)
  created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
Rule: The status column is only ever updated by the Paystack webhook handler Edge Function. The frontend may initialize a payment record as PENDING but may never mark it SUCCESSFUL. A payment is only confirmed when the backend receives and verifies the webhook from Paystack.

5.12 updated_at Auto-Update Trigger

Apply to all tables that have updated_at:

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Apply to each table:
CREATE TRIGGER set_profiles_updated_at
  BEFORE UPDATE ON profiles
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER set_requests_updated_at
  BEFORE UPDATE ON requests
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

  BEFORE UPDATE ON quotes
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

CREATE TRIGGER set_payments_updated_at
  BEFORE UPDATE ON payments
  FOR EACH ROW EXECUTE FUNCTION set_updated_at();

-- Repeat for resources, service_categories

6. Row Level Security (RLS)

RLS is the primary security layer. Enable it on every table. By default, no row is accessible to anyone. Policies selectively grant access.

Enable RLS

ALTER TABLE profiles              ENABLE ROW LEVEL SECURITY;
ALTER TABLE requests              ENABLE ROW LEVEL SECURITY;
ALTER TABLE request_status_history ENABLE ROW LEVEL SECURITY;
ALTER TABLE quotes                ENABLE ROW LEVEL SECURITY;
ALTER TABLE payments              ENABLE ROW LEVEL SECURITY;
ALTER TABLE messages              ENABLE ROW LEVEL SECURITY;
ALTER TABLE files                 ENABLE ROW LEVEL SECURITY;
ALTER TABLE notifications         ENABLE ROW LEVEL SECURITY;
ALTER TABLE resources             ENABLE ROW LEVEL SECURITY;
ALTER TABLE team_assignments      ENABLE ROW LEVEL SECURITY;
ALTER TABLE service_categories    ENABLE ROW LEVEL SECURITY;

Helper Function

CREATE OR REPLACE FUNCTION get_my_role()
RETURNS TEXT AS $$
  SELECT role FROM profiles WHERE id = auth.uid();
$$ LANGUAGE sql SECURITY DEFINER STABLE;

profiles Policies

-- Users can read their own profile
CREATE POLICY "profiles: read own"
  ON profiles FOR SELECT
  USING (id = auth.uid());

-- Admins can read all profiles
CREATE POLICY "profiles: admin read all"
  ON profiles FOR SELECT
  USING (get_my_role() IN ('admin', 'staff'));

-- Users can update their own profile
CREATE POLICY "profiles: update own"
  ON profiles FOR UPDATE
  USING (id = auth.uid());

requests Policies

-- Students can see only their own requests
CREATE POLICY "requests: student read own"
  ON requests FOR SELECT
  USING (student_id = auth.uid());

-- Students can insert requests for themselves
CREATE POLICY "requests: student insert"
  ON requests FOR INSERT
  WITH CHECK (student_id = auth.uid());

-- Students can update their own DRAFT requests only
CREATE POLICY "requests: student update draft"
  ON requests FOR UPDATE
  USING (student_id = auth.uid() AND status = 'DRAFT');

-- Admins and staff can read all requests
CREATE POLICY "requests: admin read all"
  ON requests FOR SELECT
  USING (get_my_role() IN ('admin', 'staff'));

-- Admins can update any request
CREATE POLICY "requests: admin update"
  ON requests FOR UPDATE
  USING (get_my_role() = 'admin');

messages Policies

-- Students can read messages for their own requests
CREATE POLICY "messages: student read"
  ON messages FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM requests
      WHERE requests.id = messages.request_id
      AND requests.student_id = auth.uid()
    )
  );

-- Students can insert messages into their own requests
CREATE POLICY "messages: student insert"
  ON messages FOR INSERT
  WITH CHECK (
    sender_id = auth.uid()
    AND EXISTS (
      SELECT 1 FROM requests
      WHERE requests.id = messages.request_id
      AND requests.student_id = auth.uid()
    )
  );

-- Admins and staff can read and insert all messages
CREATE POLICY "messages: admin all"
  ON messages FOR ALL
  USING (get_my_role() IN ('admin', 'staff'));

notifications Policies

-- Users can only see their own notifications
CREATE POLICY "notifications: read own"
  ON notifications FOR SELECT
  USING (user_id = auth.uid());

-- Users can update own (mark as read)
CREATE POLICY "notifications: update own"
  ON notifications FOR UPDATE
  USING (user_id = auth.uid());

quotes Policies

-- Students can read quotes for their own requests
CREATE POLICY "quotes: student read"
  ON quotes FOR SELECT
  USING (
    EXISTS (
      SELECT 1 FROM requests
      WHERE requests.id = quotes.request_id
      AND requests.student_id = auth.uid()
    )
  );

-- Only admins can create quotes
CREATE POLICY "quotes: admin insert"
  ON quotes FOR INSERT
  WITH CHECK (get_my_role() = 'admin');

-- Admins can update quotes
CREATE POLICY "quotes: admin update"
  ON quotes FOR UPDATE
  USING (get_my_role() = 'admin');

payments Policies

-- Students can read their own payments
CREATE POLICY "payments: student read own"
  ON payments FOR SELECT
  USING (student_id = auth.uid());

-- Students can insert a pending payment (to initiate Paystack)
CREATE POLICY "payments: student insert pending"
  ON payments FOR INSERT
  WITH CHECK (student_id = auth.uid() AND status = 'PENDING');

-- Students cannot update payments — only the webhook Edge Function can (uses service role)
-- Admins can read all payments
CREATE POLICY "payments: admin read all"
  ON payments FOR SELECT
  USING (get_my_role() = 'admin');

resources Policies

-- Published resources are readable by all authenticated users
CREATE POLICY "resources: read published"
  ON resources FOR SELECT
  USING (is_published = TRUE);

-- Admins can manage all resources
CREATE POLICY "resources: admin all"
  ON resources FOR ALL
  USING (get_my_role() = 'admin');

service_categories Policies

-- Everyone can read active categories
CREATE POLICY "service_categories: read active"
  ON service_categories FOR SELECT
  USING (is_active = TRUE);

-- Admins can manage categories
CREATE POLICY "service_categories: admin all"
  ON service_categories FOR ALL
  USING (get_my_role() = 'admin');

7. Authentication

Provider

Use Supabase Auth with email/password as the primary method.

Registration Flow

  1. Frontend calls supabase.auth.signUp({ email, password, options: { data: { full_name } } })
  2. Supabase sends a confirmation email
  3. The on_auth_user_created trigger fires and inserts a row into profiles
  4. Student is directed to /verify-email page
  5. After verifying, student is redirected to /app

Login Flow

  1. Frontend calls supabase.auth.signInWithPassword({ email, password })
  2. On success, Supabase returns a session (access token + refresh token)
  3. The @supabase/supabase-js client automatically stores the session in localStorage
  4. Frontend reads the user's role from profiles to determine which app section to load (/app vs /admin)

Session Management

// Listen for auth state changes
supabase.auth.onAuthStateChange((event, session) => {
  if (event === 'SIGNED_IN') {
    // fetch profile, set auth store
  }
  if (event === 'SIGNED_OUT') {
    // clear stores, redirect to /login
  }
  if (event === 'TOKEN_REFRESHED') {
    // session auto-refreshed, no action needed
  }
})

Password Reset Flow

  1. Frontend calls supabase.auth.resetPasswordForEmail(email, { redirectTo: 'https://yourdomain.com/reset-password' })
  2. User receives reset email with a link containing a recovery token
  3. Frontend at /reset-password extracts the token from the URL and calls supabase.auth.updateUser({ password: newPassword })

Role Detection

After login, fetch the user's profile to determine their role:

const { data: profile } = await supabase
  .from('profiles')
  .select('role')
  .eq('id', session.user.id)
  .single()

if (profile.role === 'admin' || profile.role === 'staff') {
  navigate('/admin')
} else {
  navigate('/app')
}

8. Storage

Buckets

Create the following buckets in Supabase Storage:

Bucket NameAccessPurpose

Bucket Policies

request-attachments — students can upload to their own request folders:

-- Allow students to upload to their own folder: request-attachments/<student_id>/*
CREATE POLICY "request-attachments: student upload"
  ON storage.objects FOR INSERT
  WITH CHECK (
    bucket_id = 'request-attachments'
    AND (storage.foldername(name))[1] = auth.uid()::TEXT
  );

-- Allow students to read their own files
CREATE POLICY "request-attachments: student read own"
  ON storage.objects FOR SELECT
  USING (
    bucket_id = 'request-attachments'
    AND (storage.foldername(name))[1] = auth.uid()::TEXT
  );

-- Allow admins to read all attachments
CREATE POLICY "request-attachments: admin read all"
  ON storage.objects FOR SELECT
  USING (
    bucket_id = 'request-attachments'
    AND get_my_role() IN ('admin', 'staff')
  );

File Path Convention

Structure file paths consistently:

request-attachments/<student_id>/<request_id>/<filename>
deliverables/<request_id>/<filename>
resources/<category>/<filename>
avatars/<user_id>/<filename>

Uploading Files (Frontend)

// services/fileService.ts
export const uploadRequestAttachment = async (
  studentId: string,
  requestId: string,
  file: File
) => {
  const path = `${studentId}/${requestId}/${Date.now()}_${file.name}`

  const { data, error } = await supabase.storage
    .from('request-attachments')
    .upload(path, file, { cacheControl: '3600', upsert: false })

  if (error) throw error

  // Insert record into files table
  await supabase.from('files').insert({
    request_id: requestId,
    uploaded_by: studentId,
    category: 'attachment',
    storage_path: data.path,
    file_name: file.name,
    file_type: file.type,
    file_size: file.size,
  })

  return data.path
}

Signed URLs (Private Files)

Never expose private storage paths directly. Generate signed URLs server-side or via Edge Function:

const { data } = await supabase.storage
  .from('request-attachments')
  .createSignedUrl(storagePath, 3600) // 1 hour expiry

// Return data.signedUrl to the frontend

9.1 accept-quote

Called when a student accepts a quote. Updates the quote status and the request status atomically.

// supabase/functions/accept-quote/index.ts
import { serve } from 'https://deno.land/std/http/server.ts'
import { createClient } from 'https://esm.sh/@supabase/supabase-js@2'

serve(async (req) => {
  const supabase = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!
  )

  const { quoteId } = await req.json()

  // 1. Get quote and verify it belongs to the authenticated user's request
  const { data: quote } = await supabase
    .from('quotes')
    .select('*, requests(student_id)')
    .eq('id', quoteId)
    .single()

  if (!quote || quote.status !== 'PENDING') {
    return new Response(JSON.stringify({ error: 'Invalid quote' }), { status: 400 })
  }

  // 2. Update quote status
  await supabase.from('quotes')
    .update({ status: 'ACCEPTED', responded_at: new Date().toISOString() })
    .eq('id', quoteId)

  // 3. Update request status to AWAITING_PAYMENT
  await supabase.from('requests')
    .update({ status: 'AWAITING_PAYMENT' })
    .eq('id', quote.request_id)

  // 4. Create a pending payment record
  await supabase.from('payments').insert({
    request_id: quote.request_id,
    student_id: quote.requests.student_id,
    quote_id: quoteId,
    amount: quote.price,
    currency: quote.currency,
    status: 'PENDING',
  })

  // 5. Send notification to student
  await supabase.from('notifications').insert({
    user_id: quote.requests.student_id,
    type: 'quote_accepted',
    title: 'Quote accepted',
    body: 'Your quote has been accepted. Proceed to payment.',
    request_id: quote.request_id,
    link: `/app/requests/${quote.request_id}`,
  })

  return new Response(JSON.stringify({ success: true }), { status: 200 })
})

9.2 initiate-payment

Calls Paystack to create a transaction and returns the payment URL or access code to the frontend.

// supabase/functions/initiate-payment/index.ts
serve(async (req) => {
  const supabase = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!
  )

  const { paymentId } = await req.json()

  const { data: payment } = await supabase
    .from('payments')
    .select('*, profiles(email), quotes(price)')
    .eq('id', paymentId)
    .single()

  // Call Paystack initialize endpoint
  const paystackRes = await fetch('https://api.paystack.co/transaction/initialize', {
    method: 'POST',
    headers: {
      Authorization: `Bearer ${Deno.env.get('PAYSTACK_SECRET_KEY')}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      email: payment.profiles.email,
      amount: Math.round(payment.amount * 100), // Paystack uses kobo
      reference: payment.id,
      metadata: {
        payment_id: payment.id,
        request_id: payment.request_id,
      },
      callback_url: `${Deno.env.get('FRONTEND_URL')}/app/payments/${payment.id}`,
    }),
  })

  const paystackData = await paystackRes.json()

  // Save Paystack reference and access code
  await supabase.from('payments').update({
    paystack_reference: paystackData.data.reference,
    paystack_access_code: paystackData.data.access_code,
    status: 'PROCESSING',
  }).eq('id', paymentId)

  return new Response(JSON.stringify({
    authorization_url: paystackData.data.authorization_url,
    access_code: paystackData.data.access_code,
    reference: paystackData.data.reference,
  }), { status: 200 })
})

// hooks/useRequestMessages.ts
import { useEffect, useState } from 'react'
import { supabase } from '@/lib/supabase'

export const useRequestMessages = (requestId: string) => {
  const [messages, setMessages] = useState<Message[]>([])

  useEffect(() => {
    // Initial load
    supabase
      .from('messages')
      .select('*, sender:profiles(full_name, avatar_url)')
      .eq('request_id', requestId)
      .order('created_at', { ascending: true })
      .then(({ data }) => setMessages(data ?? []))

    // Subscribe to new messages
    const channel = supabase
      .channel(`messages:${requestId}`)
      .on(
        'postgres_changes',
        {
          event: 'INSERT',
          schema: 'public',
          table: 'messages',
          filter: `request_id=eq.${requestId}`,
        },
        (payload) => {
          setMessages((prev) => [...prev, payload.new as Message])
        }
      )
      .subscribe()

    return () => { supabase.removeChannel(channel) }
  }, [requestId])

  return messages
}

12. Payment Integration — Paystack

Flow Overview

Student clicks "Proceed to Payment"
        ↓
Frontend calls initiate-payment Edge Function
        ↓
Edge Function calls Paystack API → gets authorization_url
        ↓
Frontend redirects to Paystack checkout (or opens popup)
        ↓

        ↓
Paystack sends webhook to paystack-webhook Edge Function
        ↓
Edge Function verifies webhook signature
        ↓
Edge Function verifies transaction with Paystack verify API
        ↓

        ↓

        ↓
Edge Function creates notification and system message
        ↓

12.1 Webhook Handler

// supabase/functions/paystack-webhook/index.ts
import { serve } from 'https://deno.land/std/http/server.ts'
import { createClient } from 'https://esm.sh/@supabase/supabase-js@2'
import { createHmac } from 'https://deno.land/std/crypto/mod.ts'

serve(async (req) => {
  const body = await req.text()
  const signature = req.headers.get('x-paystack-signature') ?? ''

  // Verify webhook signature
  const hash = createHmac('sha512', Deno.env.get('PAYSTACK_SECRET_KEY')!)
    .update(body)
    .digest('hex')

  if (hash !== signature) {
    return new Response('Unauthorized', { status: 401 })
  }

  const event = JSON.parse(body)

  if (event.event !== 'charge.success') {
    return new Response('OK', { status: 200 }) // Acknowledge but ignore
  }

  const supabase = createClient(
    Deno.env.get('SUPABASE_URL')!,
    Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!
  )

  const paystackRef = event.data.reference

  // Find the payment by Paystack reference
  const { data: payment } = await supabase
    .from('payments')
    .select('*')
    .eq('paystack_reference', paystackRef)
    .single()

  if (!payment) {
    return new Response('Payment not found', { status: 404 })
  }

  // Verify with Paystack directly (double-check)
  const verifyRes = await fetch(`https://api.paystack.co/transaction/verify/${paystackRef}`, {
    headers: { Authorization: `Bearer ${Deno.env.get('PAYSTACK_SECRET_KEY')}` },
  })
  const verifyData = await verifyRes.json()

  if (verifyData.data.status !== 'success') {
    return new Response('Verification failed', { status: 400 })
  }

  // Update payment as successful
  await supabase.from('payments').update({
    status: 'SUCCESSFUL',
    verified_at: new Date().toISOString(),
    metadata: event.data,
  }).eq('id', payment.id)

  // Update request status to PAID
  await supabase.from('requests')
    .update({ status: 'PAID' })
    .eq('id', payment.request_id)

  // System message
  await supabase.from('messages').insert({
    request_id: payment.request_id,
    sender_id: null,
    type: 'system',
    content: `Payment of ${payment.currency} ${payment.amount} confirmed.`,
  })

  // Notification
  await supabase.from('notifications').insert({
    user_id: payment.student_id,
    type: 'payment_confirmed',
    title: 'Payment confirmed',
    body: `Your payment of ${payment.currency} ${payment.amount} has been received.`,
    request_id: payment.request_id,
    link: `/app/payments/${payment.id}`,
  })

  return new Response('OK', { status: 200 })
})

13. Notifications System

Creation

Notifications are created in three ways:

  1. Directly in Edge Functions (payment confirmed, quote created, request assigned) — using the service role
  2. Database triggers (for status changes) — auto-insert when requests.status changes
  3. Admin actions (via Edge Function when admin performs an action)

Status Change Notification Trigger

CREATE OR REPLACE FUNCTION notify_on_status_change()
RETURNS TRIGGER AS $$
DECLARE
  title_text TEXT;
  body_text TEXT;
BEGIN
  IF OLD.status IS DISTINCT FROM NEW.status THEN
    title_text := 'Request status updated';
    body_text := 'Your request ' || NEW.reference || ' is now ' || NEW.status;

    INSERT INTO notifications (user_id, type, title, body, request_id, link)
    VALUES (
      NEW.student_id,
      'status_changed',
      title_text,
      body_text,
      NEW.id,
      '/app/requests/' || NEW.id
    );
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_request_status_change_notify
  AFTER UPDATE ON requests
  FOR EACH ROW EXECUTE FUNCTION notify_on_status_change();

14. Request Lifecycle

State Machine Rules

These transitions are enforced in Edge Functions and RLS. The frontend should reflect them but never be the source of enforcement.

DRAFT         → SUBMITTED       (by student: submitting the form)
SUBMITTED     → UNDER_REVIEW    (by admin: opening the request)
UNDER_REVIEW  → QUOTED          (by admin: creating a quote)
UNDER_REVIEW  → REJECTED        (by admin: rejecting the request)
QUOTED        → AWAITING_PAYMENT (by student: accepting the quote — via Edge Function)
QUOTED        → CANCELLED       (by student: declining the quote)
AWAITING_PAYMENT → PAID         (by system: Paystack webhook confirmed)
PAID          → ASSIGNED        (by admin: assigning to team member)
ASSIGNED      → IN_PROGRESS     (by admin/staff: marking work started)
IN_PROGRESS   → REVIEW          (by admin/staff: submitting for review)
REVIEW        → COMPLETED       (by admin: marking complete)
COMPLETED     → CLOSED          (by admin: archiving)
ANY           → CANCELLED       (by student or admin, with conditions)
ANY           → DISPUTED        (by student, for paid requests with issues)

Validation Function

CREATE OR REPLACE FUNCTION validate_status_transition(
  old_status request_status,
  new_status request_status,
  user_role TEXT
)
RETURNS BOOLEAN AS $$
BEGIN
  -- Define allowed transitions
  RETURN CASE
    WHEN old_status = 'DRAFT'             AND new_status = 'SUBMITTED'         THEN TRUE
    WHEN old_status = 'SUBMITTED'         AND new_status = 'UNDER_REVIEW'      AND user_role IN ('admin','staff') THEN TRUE
    WHEN old_status = 'UNDER_REVIEW'      AND new_status = 'QUOTED'            AND user_role IN ('admin','staff') THEN TRUE
    WHEN old_status = 'UNDER_REVIEW'      AND new_status = 'REJECTED'          AND user_role = 'admin' THEN TRUE
    WHEN old_status = 'QUOTED'            AND new_status = 'AWAITING_PAYMENT'  THEN TRUE
    WHEN old_status = 'QUOTED'            AND new_status = 'CANCELLED'         THEN TRUE
    WHEN old_status = 'AWAITING_PAYMENT'  AND new_status = 'PAID'              THEN TRUE
    WHEN old_status = 'PAID'             AND new_status = 'ASSIGNED'           AND user_role IN ('admin','staff') THEN TRUE
    WHEN old_status = 'ASSIGNED'          AND new_status = 'IN_PROGRESS'       AND user_role IN ('admin','staff') THEN TRUE
    WHEN old_status = 'IN_PROGRESS'       AND new_status = 'REVIEW'            AND user_role IN ('admin','staff') THEN TRUE
    WHEN old_status = 'REVIEW'            AND new_status = 'COMPLETED'         AND user_role = 'admin' THEN TRUE
    WHEN old_status = 'COMPLETED'         AND new_status = 'CLOSED'            AND user_role = 'admin' THEN TRUE
    ELSE FALSE
  END;
END;
$$ LANGUAGE plpgsql IMMUTABLE;

19. Security Guidelines

  1. Never use the service role key in the frontend. It bypasses all RLS. Only use it in Edge Functions.
  2. Always verify payment server-side. The webhook is the only source of truth for a successful payment.
  3. Validate all inputs in Edge Functions. Do not trust frontend-sent data without validation.
  4. Use parameterized queries only. Never build SQL with string concatenation.
  5. Sign all storage URLs. Private buckets must only be accessed via signed URLs with short expiry.
  6. Verify Paystack webhook signatures. Always check the x-paystack-signature header.
  7. Do not expose internal notes to students. The internal_notes field on requests must never appear in student-facing queries.
  8. Rate limiting. Enable rate limiting in Supabase for Edge Functions exposed to the public.
  9. RLS on every table. There must be no table without RLS enabled and a deny-by-default posture.
  10. Audit trail. The request_status_history table provides a full audit trail. Do not allow it to be deleted.
