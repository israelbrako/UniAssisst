1. Overview

UniAssist is a student support platform where students can request academic, technical, and project-related assistance. The frontend is the complete visual and interactive layer for three user types:

  • Visitors — browsing the public website
  • Students — authenticated users managing their requests
  • Administrators — internal team managing the platform

The frontend is being built independently by three developers as a design competition. The strongest implementation will be selected and become the foundation of the final production application. All three implementations must follow this specification so they remain compatible with the same backend.

Important: Use realistic mock data during this phase. Do not hard-code data in a way that makes backend integration difficult later. Structure everything around the real data model described in this document.

5. Branding & Visual Identity

UniAssist is built under Balerioncodes. The visual identity should reflect a premium, modern SaaS/EdTech product — not a generic university portal.

Balerioncodes Brand Colors

Use these as your foundation. Minor adjustments are allowed for contrast and accessibility.

/* Suggested palette — adapt as needed */
--color-primary:     #6C3CE1;   /* Deep violet — primary brand */
--color-primary-dark:#5128C9;
--color-accent:      #A78BFA;   /* Light violet — accents */
--color-bg:          #0F0E17;   /* Dark background */
--color-surface:     #1A1826;   /* Card/panel surfaces */
--color-border:      #2E2A3B;   /* Borders */
--color-text:        #F0EFF4;   /* Primary text */
--color-muted:       #8B8998;   /* Secondary/muted text */
--color-success:     #34D399;
--color-warning:     #FBBF24;
--color-error:       #F87171;
You may use a light theme variant. Keep brand recognizable. Avoid randomizing the color palette entirely.

Typography

  • Headings: A premium sans-serif (e.g., Inter, Geist, or DM Sans)
  • Body: Same family, regular weight
  • Mono: JetBrains Mono or Fira Code (for code, request IDs, references)

What to Aim For

  • Strong whitespace and breathing room
  • Consistent spacing scale (use Tailwind's default scale)
  • Subtle shadows (shadow-sm, not heavy drop shadows)
  • Refined borders (border border-border)
  • Status badges with clear color coding

What to Avoid

  • Excessive glassmorphism
  • Too many gradient layers
  • Overly rounded "bubbly" cards
  • Cluttered dashboards with too much information density
  • Generic bootstrap/template aesthetics

7. Pages & Features

7.1 Landing Page

Sections (in order):

  1. Navigation — Logo, nav links (Home, Services, How It Works, Resources, About), Sign In + Get Started buttons
  2. Hero — Headline: "Academic support, without the stress." Primary CTA: Get Help, Secondary CTA: Explore Services. Include a product UI mockup or request card visual.
  3. Services Preview — Cards for Academic Support, Technical Support, Project Support, Resources
  4. How It Works — 4-step process: Submit → Review → Quote → Support
  5. Trust / Stats — Placeholder metrics (students helped, requests completed, rating, availability). Label as demo data.
  6. Testimonials — Realistic placeholder testimonials. Build with a data array so real data can be swapped in.
  7. Final CTA — "Stuck on something? Let UniAssist help you move forward." + Get Started button
  8. Footer — Links, socials, copyright

7.2 Authentication Pages

  • Login — Email + password. Link to register and forgot password.
  • Register — Full name, email, phone, university, department, level, student ID, password, confirm password. Validation on all fields.
  • Forgot Password — Email input. Submit sends reset link (mock for now).
  • Reset Password — New password + confirm. Token from URL params.
  • Email Verification — Confirmation screen with resend option.

7.3 Student Dashboard (/app)

  • Time-based greeting: "Good afternoon, Alex."
  • Stats row: Active Requests, Pending Requests, Completed Requests, Total Spent
  • Active request cards (title, category, status badge, progress bar, deadline, assigned member)
  • Recent activity feed (quote received, payment confirmed, new message, etc.)

7.4 Create Request (/app/requests/new)

Multi-step wizard with progress indicator:

StepContent
1Select Category (Academic, Technical, Project, Research & Writing, Other)
2Request Details (title, description, subject/course, department, technology)
3Deadline (preferred date picker, urgency selector)
4File Upload (PDF, DOCX, PPTX, ZIP, images, source code)
5Contact Information (pre-filled from profile, editable)
6Review (summary of all inputs)
7Confirmation (success screen, generated reference e.g. REQ-10482)

Use React Hook Form with Zod schemas per step. Preserve state across steps (Zustand or multi-step form context).

7.5 Request Details (/app/requests/:id)

  • Request header: ID, title, category, status badge
  • Progress timeline showing all lifecycle states
  • Description and deadline
  • Assigned team member card
  • Quote section (if quoted: price, services, accept/decline actions)
  • Payment section (if awaiting payment: amount, proceed to pay button)
  • Files tab: uploaded files with name, type, size, date
  • Messages tab: conversation thread (see section 7.6)
  • Deliverables tab: files from team
  • Status history log

7.6 Messaging

Per-request conversation view:

  • Message bubbles (student vs team member, different alignment/color)
  • Timestamps on each message
  • File attachment display inline
  • System event messages styled differently (e.g. gray italic: "Payment confirmed — 14 Jan 2026")
  • Message input with attach file button
  • Architecture must support future Supabase Realtime subscription

7.7 Payments (/app/payments)

  • List of payments with: request title, amount, status, transaction reference, date
  • Payment detail page: full breakdown, Paystack reference, status
  • The frontend must never confirm a payment — display "Awaiting confirmation" until backend confirms

7.8 Notifications

  • Bell icon in navbar with unread count badge
  • Dropdown showing recent 5–10 notifications
  • Full notifications page at /app/notifications
  • Notification types: request updates, quotes, payments, messages, files, completions

7.9 Resource Library

  • Category filter tabs: Study Guides, Past Questions, Programming, Research, Project Ideas, Career
  • Resource cards: title, description, category, author, date, download/view button
  • Build with a data array to allow future database connection

7.10 Admin Dashboard (/admin)

  • Stats: new requests, active requests, completed, revenue, pending payments
  • Team workload section
  • Recent activity feed
  • Quick links to request queue

7.11 Admin Request Management (/admin/requests)

  • Full data table: request ID, student, category, status, deadline, assigned, date
  • Search bar
  • Filter by: status, category, date range, assigned member
  • Sort by: date, status, deadline
  • Row click → Request Details

8. State Management

Guidelines

  • Use useState and useContext for local/simple UI state (modals open, tab selection, form steps)
  • Use Zustand for application-level state that crosses multiple components

Suggested Zustand Stores

// store/authStore.ts
// currentUser, isAuthenticated, role, login(), logout()

// store/requestStore.ts
// activeRequests, draftRequest (multi-step form state), setDraftField()

// store/notificationStore.ts
// notifications[], unreadCount, markRead()

// store/uiStore.ts
// sidebarOpen, theme (light/dark), toasts

9. Forms & Validation

Use React Hook Form + Zod for all forms.

Example — Registration Schema

// lib/validators/registerSchema.ts
import { z } from 'zod'

export const registerSchema = z.object({
  fullName: z.string().min(2, 'Full name is required'),
  email: z.string().email('Invalid email address'),
  phone: z.string().min(7, 'Phone number is required'),
  university: z.string().min(2, 'University is required'),
  department: z.string().min(2, 'Department is required'),
  level: z.string().min(1, 'Level is required'),
  studentId: z.string().min(1, 'Student ID is required'),
  password: z.string().min(8, 'Password must be at least 8 characters'),
  confirmPassword: z.string(),
}).refine(data => data.password === data.confirmPassword, {
  message: 'Passwords do not match',
  path: ['confirmPassword'],
})

Example — Request Step 2 Schema

export const requestDetailsSchema = z.object({
  title: z.string().min(5, 'Title must be at least 5 characters'),
  description: z.string().min(20, 'Please provide more detail'),
  subject: z.string().optional(),
  department: z.string().optional(),
  technology: z.string().optional(),
})

11. Backend Integration Readiness

The frontend must be built for easy backend connection. Follow this pattern:

Service Layer

Never call Supabase or any API directly from components. All data calls go through src/services/.

// services/requestService.ts
export const getRequests = async (userId: string) => {
  // Phase 1: return mockRequests
  // Phase 2: return supabase.from('requests').select('*').eq('student_id', userId)
}

Type Definitions

Define all data types in src/types/. These must mirror the backend data models.

// types/request.ts
export type RequestStatus =
  | 'DRAFT' | 'SUBMITTED' | 'UNDER_REVIEW' | 'QUOTED'
  | 'AWAITING_PAYMENT' | 'PAID' | 'ASSIGNED' | 'IN_PROGRESS'
  | 'REVIEW' | 'COMPLETED' | 'CLOSED' | 'CANCELLED' | 'REJECTED' | 'DISPUTED'

export interface Request {
  id: string
  studentId: string
  title: string
  description: string
  category: RequestCategory
  status: RequestStatus
  deadline: string
  createdAt: string
  updatedAt: string
  assignedTo?: TeamMember
  progress?: number
  quoteId?: string
  paymentId?: string
}

12. Component Conventions

  • Use named exports for all components
  • One component per file
  • Co-locate styles within the component using Tailwind classes
  • No inline styles unless absolutely necessary
  • Props must be typed with TypeScript interfaces
  • Use cn() utility from shadcn for conditional class merging
// components/common/StatusBadge.tsx
interface StatusBadgeProps {
  status: RequestStatus
}

export const StatusBadge = ({ status }: StatusBadgeProps) => {
  const variants: Record<RequestStatus, string> = {
    IN_PROGRESS: 'bg-blue-500/10 text-blue-400 border-blue-500/20',
    COMPLETED: 'bg-green-500/10 text-green-400 border-green-500/20',
    // ...
  }
  return (
    <span className={cn('px-2 py-1 rounded text-xs font-medium border', variants[status])}>
      {status.replace(/_/g, ' ')}
    </span>
  )
}

13. Responsive Design

The application must work on desktop, laptop, tablet, and mobile. Mobile is not a compressed desktop view.

Breakpoints (Tailwind defaults)

Navigation

  • Desktop: full horizontal navbar
  • Mobile: hamburger menu → slide-out drawer

Dashboards

  • Desktop: sidebar + main content
  • Tablet: collapsible sidebar
  • Mobile: bottom navigation bar or drawer

Tables

  • Desktop: full data table
  • Mobile: card-based list view

14. Performance Guidelines

  • Lazy-load all route pages using React.lazy + Suspense
  • Use Skeleton components for all loading states (no spinner-only states)
  • Memoize expensive components with React.memo where appropriate
  • Avoid prop drilling beyond 2 levels — use context or Zustand
  • Keep bundle size lean — do not install libraries that can be done with Tailwind or existing stack

15. Developer Notes

  • Each developer builds their own independent implementation in their own repository
  • All three must follow the same routing structure and type definitions
  • This ensures that when the winning frontend is selected, the team can connect the backend without restructuring the data layer
  • The multi-step request creation form and the request details page are the most complex screens — prioritize getting them right
  • Messaging UI should be built with Supabase Realtime in mind even though it will use mock data now
  • Payment pages must never allow frontend-side payment confirmation
